<h2>一、三条不能让的底线</h2>
<p>先把底线划出来，后面的取舍才有边界。底线只有三条，任一条不过，方案直接否掉，不必再谈价格。</p>
<h3>出口必须是可查的独立地址</h3>
<p>判定门槛：每条线路有独立出口，能用 ipinfo.io 查到 ASN 与机构名，且机构名属于当地运营商。如果服务商只给一个共享地址，或者查询结果显示托管商，直接排除。这不是苛刻，而是换人之后唯一能自证的凭据。</p>
<h3>一号一环境要能落实到文件</h3>
<p>判定门槛：每个号的环境配置有独立文件或独立实例，命名规则统一，能一眼看出对应关系。做不到这一条，交接时必然出现「这个号到底用哪个环境」的争执，演示前一天最怕这种争执。</p>
<h3>账目能按号、按线拆开</h3>
<p>判定门槛：月结单能给出每个号或每条线的用量，而不是只有一个总数。团队报销、成本分摊、后续扩容判断都依赖这个粒度，缺了就永远在猜钱花在哪。</p>
<h2>二、选型打分表：六项，每项五分</h2>
<p>底线之外的项目按分数取舍，总分三十，二十四分以上可以合作，十八到二十三分适合小量试用，十八分以下直接跳过。打分要写理由，理由比分数重要。</p>

<h2>三、交接要留下的四类记录</h2>
<p>交接记录不是写给领导看的报告，是写给下一个接手人的操作手册。判断标准很简单：一个没参与过这个项目的人，照着记录能不能在半小时内让业务跑起来。不能，就是记录不合格。</p>
<h3>线路台账</h3>
<p>字段建议固定为：线路 ID、出口地址、ASN、地区、绑定号、开通日期、到期日、最近核对时间、当前状态。线路 ID 用「地区-序号」的形式，别用随机字符串，人看得懂才记得住。</p>
<h3>环境与规则文件</h3>
<p>每个号的环境配置、分流规则、启动脚本统一放一个仓库，目录结构按号分文件夹，文件名带版本号。仓库里再放一份 README，写清启动顺序和常见报错的处理办法，比口头交代有效十倍。</p>

<h2>四、客户演示前的半小时检查</h2>
<p>演示是唯一不能重来的场景，检查要按固定顺序，别临场发挥。顺序建议从外到内：线路、环境、账号、话术。</p>
<h3>线路与环境三分钟过一遍</h3>
<p>查当前出口的 ASN 与城市是否与演示账号一致；开一个空白页面看时区、语言、分辨率是否与上次演示相同；确认演示账号的登录态还在，不需要重新验证。三件事加起来不超过三分钟，能挡掉大部分临场尴尬。</p>
<h3>账号侧只做只读操作</h3>
<p>演示前不要改密码、不要换绑、不要调整资料，任何写操作都可能触发额外确认。真要改，提前一天改完并留出观察窗口。演示账号最好固定一条线，别和其他日常号共用，减少相互影响。</p>
<h2>五、换人当天的五步接手流程</h2>
<p>五步是：拿到台账与仓库权限、按 README 起一套环境、用测试号跑通一次登录与对话、核对账单与线路数量是否一致、在台账上签名确认。前四步任何一步卡住，都说明交接记录有缺口，当场补，别留到下周。</p>
<p>签名这一步别省。签了名代表「我确认这套东西能跑」，后面出问题有明确的起点，团队里少很多「我以为」。</p>
<h2>常见问答</h2>
<h3>团队只有三个人，也需要这么正式吗？</h3>
<p>答：人越少越需要，因为一个人的离开占比更大。三个人也能用这套清单，只是把会议改成表格留言，把审批改成群里一句话确认，核心是记录不缺项，形式可以轻。</p>
<h3>服务商不给导出台账怎么办？</h3>
<p>答：先看后台有没有接口或页面能批量看线路信息，能用浏览器脚本抓一次也行；都不行就手工录一次，之后每次变更补一行。这一项在选型打分里本来就该扣分，长期看建议换一家支持导出的。</p>
<h3>演示用账号和平常号要不要分开？</h3>
<p>答：建议分开。演示号需要稳定和可控，日常号可能频繁试新配置，两者混在一起，一次配置失误就会在客户面前暴露。分开的成本只是多一条线和一套环境，收益是演示可控。</p>
<h3>交接记录多久复盘一次？</h3>
<p>答：换人时必查，另外每季度自查一次。自查内容很简单：按记录起一套环境，看能不能跑通。跑不通说明记录已经过期，趁没出事赶紧补，比出事之后再翻记录省事得多。</p>
